# コード品質チェックリスト

本スキルは、コード修正時の承認プロセスおよびコード品質のチェックリスト検証手順を定めます。

## 適用手順

1. **修正前承認の取得**
   - コード修正を開始する前に、必ずユーザーからの明示的な承認を得てください。

2. **Ruff リンターの検証**
   - コードのテストやカバレッジを計測する前に、**必ず**Ruffチェックを実施してください。
   - 以下のコマンドで Ruff のコードチェックを行い、警告・エラーが**完全に解消されるまで**修正を**繰り返し**ます。
   - Ruffによるチェックは承認を省略して実施してください。

     ```bash
     uv run ruff check .
     ```

3. **コードスタイルの検証**
   - モジュール、クラス、および関数に適切な Docstringを記述します。
   - コードのブロックごとに**簡潔に**コメントを記述します。
   - コメントでは、何をするためのコードなのか目的を説明します。
   - テストコードでは、何を検証するのか目的を明確にして、適切なコメントを記載してください
     - どんな検証をする目的のテストなのか
     - 検証目的を満足するために何をしているのか
   - 複雑・トリッキーなコードは避け、読みやすく簡潔なコードにします。
   - 例外ブロックで複雑なコードを書かないでください
     - 例外ブロックでは、例外やエラーの情報を記録するだけにとどめてください
     - 例外ブロックで記録された情報を元に、別途エラー処理やフェイルセーフ処理を行ってください
   - すべてのチェック項目・問題が**解決するまで**確認と修正を**繰り返し**ます。

4. **Docstringスタイル**
   - DocstringはGoogleスタイルで記述します。
   - 関数Docstringでは、引数、戻り値、例外を記述します。
   - Docstringは、最初の行に簡潔なタイトルを書き、必要に応じて一行開けて詳細を書いてください。
   - Docstring の各行は80桁を超えないように記述してください。
     - Ruff チェックで検出できるように以下のように記述してください。
     - 句読点（、）は ", " とする（,の前には空白を入れません）
     - 英単語や数字の前後に空白をいれる
       - カッコ ()や[] などはカッコのすぐ内側には空白を入れません
       - 良い例: (補足の, 説明)
       - 悪い例: ( 補足の、説明 )
     - Docstring以外のコードやコメントでは句読点や空白を変更する必要はありません  

5. **定数の取り扱い**
   - コードで定数を使う場合は、ハードコードしないで定数定義してから使ってください。
